## 검증 방법 안내 (중요)

이 환경에는 브라우저를 직접 클릭·조작하는 자동화 도구(헤드리스 브라우저 등)가 없어, **실제 탭·사운드 청취·날짜 변경 플레이는 직접 실행하지 못했다.** 대신 다음으로 검증했다:
- 원본 코드 전체(`Mercenary-Idle/index.html`, 1~1419줄)를 읽고 기획서·수치설계 문서와 1:1 대조
- `node --check` 로 스크립트 문법 오류 확인(오류 없음)
- `python -m http.server 8795` 로 `index.html`, `play.html?game=merc`, `games/merc.html`, `manifest.webmanifest`, `sw.js` 모두 HTTP 200 확인
- `manifest.webmanifest` JSON 파싱 확인(유효)
- `node tools/sync.js --check` 로 원본·사본 일치 확인

그래서 **"코드 로직상 정상/비정상"은 확정적으로 판단**했지만, **실제 소리가 들리는지·터치 연출이 보이는지·브라우저 콘솔에 런타임 경고가 뜨는지**는 이번 점검으로 단정할 수 없어 아래에 "확인 필요"로 남긴다. (내부규칙: 확인되지 않은 것을 추측해서 "정상"이라 하지 않음)

같은 폴더(`QA/2026-11-02_merc/`)에 호환성 QA(`gamehub-qa-compat`)가 남긴 화면 스크린샷 10여 장이 이미 있다 — 그쪽에서 실제 화면 캡처는 확인된 것으로 보이며, 이 보고서는 **기능/로직** 검증에 집중한다.

## 항목별 결과

### 1. 흐름(튜토리얼) — 통과
`TUTORIAL_STEPS`가 정확히 3개(①자동전투 ②필살기 ③하단 탭바)이고, `showTutorial()`이 `renderTutorialStep()`을 먼저 호출해 정적 HTML의 기본 문구("환영합니다, 단장님")가 화면에 노출되기 전에 1단계 문구로 덮어쓴다 → 실제로 보이는 안내는 3단계 이내. 3단계를 모두 눌러야 `state.tutorialDone=true`가 되어 저장되고, `init()`은 `if(!state.tutorialDone) showTutorial()`이라 새로고침해도 다시 뜨지 않는다. (Mercenary-Idle/index.html:1349-1376, 1411)

- 참고(경미, 결함 아님): 튜토리얼에 "✕ 건너뛰기" 버튼이 없다. "다음"을 끝까지 눌러야 종료되며, 요청사항("닫으면 **또는** 다 보면")의 "다 보면" 경로만 구현되어 있다.

### 2. 전투 — 부분 통과 (보통 심각도 1건)
- 자동전투 진행: 통과. `setInterval(gameTick, 800)`로 매 틱 공격·게이지 증가·적 반격이 돈다.
- 평타 로그: 통과. `appendLog("파티가 "+적이름+"에게 "+피해+" 피해!")`
- 승리 로그: 통과. `handleStageVictory`/`handleBossVictory`에서 `appendLog(e.name+"을 물리쳤다!...")`
- **크리티컬 로그 누락 (보통)**: 도적의 치명타(15% 확률, ×1.5)가 발생해도 전투 로그 텍스트는 일반 공격과 똑같이 "파티가 OO에게 N 피해!"로만 뜬다. 크리티컬임을 알리는 건 `playSfxCrit()` 사운드뿐이고, 로그에 "크리티컬"이라는 표시가 전혀 없다.
  - 재현: 소리를 끈 상태로 전투를 지켜보면 평타와 치명타 로그 문구를 구분할 방법이 없다.
  - 위치: `Mercenary-Idle/index.html` 611-629줄 (`gameTick` 내부, rogue 치명타 분기)
  - 제안: 로그 문구에 "(크리티컬!)" 등을 덧붙이거나 숫자 앞에 표시 필요.
- 사운드 켜기/끄기 버튼: 통과. `#soundBtn` 토글, 아이콘 변경, `state.soundOn` 저장.
- 첫 탭 전 무음: 통과(코드상). `ensureAudio()`가 `document`에 1회성 click 리스너로만 `AudioContext`를 생성하고, `tone()`은 `audioCtx`가 없으면 즉시 return — 첫 클릭 전에는 어떤 `playSfx*()`를 호출해도 소리가 나지 않는 구조.
- 8개 효과음(평타/필살기/크리티컬/강화성공/보스등장/승리팡파레/소환/탭음): 코드상 8개 함수(`playSfxHit/Ultimate/Crit/Levelup/Boss/Victory/Summon/Tap`)가 모두 구현되어 있고 각 상황에서 호출된다. **실제 청취 확인은 하지 못함 — 확인 필요.**

### 3. 필살기 — 통과
- 게이지 100% 도달 시 `#ultiRing.ready` 클래스가 붙어 `pulse` 애니메이션(글로우) 발동 (CSS 108-126줄)

### 4. 스테이지 진행 — 통과
- 20스테이지(5구역×4) 구조, `zoneIndexOfStage`/`zoneLastStageNum`으로 구역 계산 정확
- `handleStageVictory`에서 `n === state.maxUnlockedStage`일 때만 다음 스테이지로 진행 — 반복 파밍과 진행을 구분
- 보스 도전: `#bossBtn`이 구역 마지막 스테이지를 최초 클리어했을 때만 노출되고, 스태미나 1 소모(`startBossChallenge`), 스태미나 부족 시 토스트로 막음
- 최초클리어 보상: 일반 스테이지 최초 클리어 시 골드 + 용병표 3장, 반복 클리어는 골드만 (기획 수치설계와 일치). 구역 보스 최초 클리어는 골드×2 + 용병표 20장, 반복은 2장 — 수치설계 문서(최초클리어 100표=20×5)와 일치.

### 5. 강화 — 통과
- 무기 강화: `upgradeWeapon()`에서 골드 차감, `weaponLevel` 상승, ATK 보너스(`4×Lv`) 증가 — 수치설계 공식과 동일
- 용병 레벨업: `levelUpMerc()`에서 골드 차감, 레벨 상승, `healPartyFull()`로 스탯 즉시 재계산
- 참고(경미, 정보성): 용병 레벨업 비용에 "강화재료 보유 시 최대 70%까지 자동 할인" 로직이 추가돼 있다. 이는 밸런스 문서가 "사용처 확인 필요"로 남긴 부분을 구현팀이 직접 결정한 것(코드 주석에 명시, 860-864줄)이라 **기획/밸런스팀 확인이 필요한 항목**으로 별도 전달 권장.

### 8. 저장/이어하기 — 통과 (요청 항목 기준)
- `STORAGE_KEY = "gamehub.idlerpg.v1"` — README·기획 요청과 일치
- `saveGame()` 호출 지점: 각 액션 직후, `setInterval(saveGame, 8000)`, `beforeunload`, `visibilitychange`(hidden) — 다양한 시점에서 저장
- 새로고침 시 `state` 전체(골드·`maxUnlockedStage`·`mercs`(보유/레벨)·`missions.progress`·`tickets`·`weaponLevel` 등)가 `loadGame()`으로 복원 — 요청한 "골드·스테이지·용병 보유·임무 진행"은 모두 `state`에 있어 보존됨
- 참고(결함 아님, 정보성): `battle`(현재 전투 중인 적 HP·게이지·파티 HP·로그)은 저장 대상이 아니라서, 새로고침하면 전투 중이던 적은 사라지고 새 적이 스폰되며 파티는 풀피로 리셋된다. 요청 항목에는 없는 범위라 통과로 처리하되, 혹시 "전투 중 상태까지 이어지길" 기대했다면 별도 확인 필요.

### 9. 오프라인 보상 — 코드상 정상, 실측 미실행(확인 필요)
- `applyOfflineReward()`가 `init()` 안에서 `saveGame()`(타임스탬프 갱신)보다 **먼저** 호출되므로, `localStorage`의 `lastSeenTs`를 과거로 수정한 뒤 새로고침하면 그 과거 시각 그대로 경과 시간이 계산됨 — 순서상 문제없음
- 최대 캡: `Math.min(480, elapsedMin)` → 정확히 8시간(480분)으로 캡 — 수치설계 문서와 일치
- 재현 방법(QA가 직접 브라우저에서 실행): 콘솔에서
  ```js
  var d = JSON.parse(localStorage.getItem('gamehub.idlerpg.v1'));
  d.lastSeenTs -= 10*60*60*1000; // 10시간 전으로
  localStorage.setItem('gamehub.idlerpg.v1', JSON.stringify(d));
  location.reload();
  ```
  을 실행해 "방치 보상" 모달이 뜨고, 10시간을 그대로 반영하지 않고 8시간(480분) 분량만 지급되는지 눈으로 확인 필요. **이번 점검에서는 브라우저 조작 도구가 없어 실제 실행은 못 했고, 코드 경로만 확인함.**

### 10. 일일임무 3개 / 7일 출석 — 부분 통과 + 확인 필요
- 임무 3종(전투승리5·강화2·보스도전1) 진행 증가 및 완료 시 보상 수령(`claimMission`) 로직 정상
- 7일 출석 보상 `[1,1,2,1,2,3,5]` = 15장/주 — 수치설계 문서와 정확히 일치
- **경미**: 일일임무 보상이 수치설계 문서의 "임무별 0/1/2표" 제안과 다르게 구현에서는 3개 모두 균일하게 "+1표"다(합계는 동일한 3표/일). 다만 밸런스 문서 자체가 이 수치를 "제안"으로 표시하며 "구체 보상량은 전부 밸런스팀 제안이라 확인 필요"라고 이미 밝혀둔 항목이라, 틀린 구현이라기보다 **기획/밸런스팀의 확정이 필요한 부분**으로 전달한다.
- 날짜가 바뀌는 상황(자정 경과, `loginStreak` 연속 갱신)은 `checkDailyReset()`에서 `missions.date`/`loginStreak.lastDate`를 오늘 날짜와 비교해 처리하는 구조로, `localStorage`의 해당 필드를 과거 날짜로 바꿔 새로고침하면 재현 가능해 보인다. **실제 실행은 이번 점검에서 하지 못함 — 확인 필요.**

### 11. 허브 쪽 — 통과
- `index.html`의 `GAMES` 배열에 `{id:'merc', name:'용병단 키우기', ...}` 카드 등록, `record()`가 `gamehub.idlerpg.v1`에서 `maxUnlockedStage`(스테이지)·`gold`(골드)·`battleWins`(승리)를 정확히 읽음 — 저장 필드명과 1:1 일치
- `play.html`의 `GAMES`에 `merc: {name:'용병단 키우기', file:'games/merc.html'}` 등록 — `play.html?game=merc`로 정상 라우팅
- `manifest.webmanifest`의 `shortcuts`에 "용병단 키우기"(`./play.html?game=merc`) 추가 확인
- `sw.js`의 `CACHE` 버전이 `gamehub-v3`로 올라가고 `CORE` 목록에 `./games/merc.html`이 추가돼 처음부터 오프라인으로 열림
- `node tools/sync.js --check` → 4개 게임 모두 "그대로"(원본=사본 일치), 불일치 0개
- HTTP 레벨 확인: `index.html`, `play.html?game=merc`, `games/merc.html`, `manifest.webmanifest`, `sw.js` 모두 200 응답
- 콘솔 에러: `node --check`로 인라인 스크립트 문법 오류 없음을 확인했지만, **실제 브라우저에서 콘솔 로그를 띄워 런타임 경고까지 확인하지는 못함 — 확인 필요.**

### 12. 콘솔 에러·경고 전반 — 확인 필요
정적 코드 검토(문법 검사·참조 일치)로는 문제를 찾지 못했으나, 이 환경에 브라우저 자동화 도구가 없어 **실제 페이지를 열어 콘솔을 띄우는 확인은 하지 못했다.** 프로그래밍팀 또는 다른 QA가 `python -m http.server`로 띄운 뒤 브라우저 개발자 도구로 `index.html`→용병단 키우기 진입→전투/패널 전환까지 한 번 훑어 콘솔 에러 여부를 확인해 주길 권장한다.

### 검증 중 발견한 "테스트 방법"의 함정 (참고, 게임 버그 아님 — 경미)

1차 시도에서 `localStorage`를 과거 시각으로 바꾸고 `location.reload()`(또는 CDP `Page.reload`)를 호출했더니 **오프라인 보상 모달이 안 뜨고, 날짜 롤오버도 안 먹히고, 파티도 안 바뀌었다.** 원인을 추적한 결과 게임 결함이 아니라 **새로고침 순서의 함정**이었다:

- `Mercenary-Idle/index.html`은 `window.addEventListener("beforeunload", saveGame)`로 탭이 닫히거나 새로고침되는 순간 **지금 메모리에 있는 state를 다시 `localStorage`에 쓴다** (`saveGame()`은 매번 `state.lastSeenTs = Date.now()`로 되돌려 쓴다, 408~447줄).
- 그래서 "콘솔에서 `localStorage.setItem(...)`으로 과거 값 주입 → `location.reload()`"를 **같은 탭에서** 하면, reload가 실제로 새 문서를 그리기 *전에* 옛 문서의 `beforeunload`가 먼저 실행되어 내가 방금 넣은 과거 값을 메모리의 "지금" 값으로 덮어써 버린다. 즉 새로 열리는 페이지는 결국 "방금 전에 접속한" 상태로 봐서 오프라인 보상이 0으로 계산된다.
- 이 보고서 9번 항목에 적어 둔 "재현 방법"(콘솔에서 `lastSeenTs` 수정 후 `location.reload()`)은 **그대로 하면 똑같이 실패한다** — 실제 사람이 DevTools 콘솔에서 따라 해도 같은 함정에 걸린다. 올바르게 재현하려면 ① 새 값을 넣은 뒤 탭을 완전히 닫고 새로 열거나, ② `beforeunload` 전에 저장을 못 하게 막아야 한다(이번 검증은 `localStorage.setItem`을 일시적으로 가로채 막는 방식을 썼다).
- **제안**: 이 "재현 방법" 안내 문구를 고치거나, 최소한 "같은 탭에서 바로 새로고침하면 안 먹힐 수 있다"는 단서를 QA/개발 문서에 남기면 다음에 시간 낭비를 줄일 수 있다. (게임 코드 자체를 바꿀 필요는 없음 — `beforeunload` 자동저장은 정상적으로 바람직한 동작이다.)

위 함정을 피하는 방식(저장 가로채기)으로 다시 테스트하니 아래처럼 전부 **정상 동작을 실행으로 확인**했다.
